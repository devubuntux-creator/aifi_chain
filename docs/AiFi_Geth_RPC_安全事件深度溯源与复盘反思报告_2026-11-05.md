## Executive Summary（执行摘要）

2026 年 11 月初，AiFi 链核心节点 `n_AiFi-Rpc1`（`124.243.174.69`）出现管理员 SSH 无法登录现象。经深度溯源与现场证据链取证，确认该事件系由**外部黑客针对 Geth 节点 RPC 漏洞进行的系统性扫描与漏洞利用**所致。

黑客利用 Nginx 网关未过滤 `debug` 命名空间、节点配置默认启用 `debug` 模块且 **Geth 进程以 `root` 超级管理员身份运行** 的系统级安全短板，调用 Geth 原生性能分析接口 `debug_writeMemProfile` 强行覆盖写入敏感文件，导致 `Rpc1` 节点的 `/root/.ssh/authorized_keys` 被 gzip 格式的 pprof 二进制数据污染损毁，进而导致合法管理员 SSH 密钥失效失联。

目前，应急小组已通过**云端在线免重启穿透夺回控制权**、**Nginx 全局高性能 Lua WAF 阻断**、**节点底层 Geth 危险模块滚动热下线**三道防线彻底排除了安全隐患，**全网业务及链上出块保持 100% 连续性，实现业务零停机、资产零损失**。

## 二、 漏洞机理与技术剖析

### 1. Geth `debug_writeMemProfile` 任意文件写入漏洞
* **成因**：Geth 的 `debug` 命名空间中提供了 `debug_writeMemProfile(file)` 等诊断方法，允许将运行时的 Go runtime profile 写入指定路径。
* **设计缺陷**：官方未对传入的 `file` 文件路径做任何合法性校验（没有做路径穿越限制，也没有做文件类型限制）。如果 Geth 以超级管理员 `root` 运行，调用方可指定写入操作系统的**任意绝对路径**（包括 `/etc/cron*`、`/root/.ssh/authorized_keys`、`/etc/shadow` 等）。

### 2. 为什么攻击者没能直接拿到 Shell？
* `debug_writeMemProfile` 写入的内容是 Golang 的 `runtime/pprof` 采集数据，采用 **Gzip 压缩的 Protocol Buffers 格式**。
* 攻击者无法自由控制文件开头的魔数（开头固定为 Gzip 头 `0x1F 0x8B`）。
* 因此，写入 `/root/.ssh/authorized_keys` 时，sshd 解析其为乱码，直接拒绝对其授权，反而将机器“锁死”；写入 `/etc/crontab` 时，cron 守护进程同样会报语法错误而拒绝执行。黑客虽然破坏了文件，但未能成功提权植入持久后门。

## 三、 根因分析（Root Cause Analysis）

本次事件暴露了我们在区块链基础设施架构与运维管理上的多重盲区：

```
                    ┌──────────────────────────────────────────┐
                    │  根因 1: 权限配置过度宽泛 (Least Privilege)  │
                    │  Geth 节点进程直接使用 root 用户启动      │
                    └────────────────────┬─────────────────────┘
                                         │
                                         ▼
                    ┌──────────────────────────────────────────┐
                    │  根因 2: 危险调试模块暴露 (Unsafe API)    │
                    │  config.toml 默认开启 debug 与 txpool    │
                    └────────────────────┬─────────────────────┘
                                         │
                                         ▼
                    ┌──────────────────────────────────────────┐
                    │  根因 3: 网关防御策略存在疏漏 (WAF Gap)   │
                    │  Nginx 早期仅阻断了 setHead 单一方法     │
                    └────────────────────┬─────────────────────┘
                                         │
                                         ▼
                    ┌──────────────────────────────────────────┐
                    │  根因 4: 资产清单更新脱节 (Asset Tracking)│
                    │  已下线淘汰的 Archive-02 仍在本地配置中   │
                    └──────────────────────────────────────────┘
```

1. **违背最小权限原则（Principle of Least Privilege）**：
   * `aifichain.service` 中直接配置 `User=root` 运行区块链节点。若采用独立的 `geth` 降权非特权账号，黑客根本无权写入 `/root/.ssh/` 或 `/etc/` 目录。
2. **生产环境开放调试接口（Dangerous API Exposure）**：
   * 生产节点的 `HTTPModules` 盲目照搬开发配置，开启了 `debug`、`txpool` 等高危或消耗性接口，造成了致命的攻击面。
3. **网关层防御存在盲区**：
   * 之前的 Nginx 策略仅防范了 `debug_setHead`（回滚区块），没有从架构上把整个 `debug` 命名空间彻底隔绝在外网之外。
4. **资产管理台账脱节**：
   * 淘汰注销的机器未及时在运维团队、SSH Config 和监控资产库中归档删除，增加了排查干扰和沟通成本。

## 四、 应急响应与处置措施总结

在本次处置过程中，团队采取的系列动作堪称高可用运维的典范：

1. **第一道防线：零业务中断止血（毫秒级）**
   * 在 Nginx 网关通过 Lua 引擎精准过滤请求 Body，不区分大小写拦截所有 `debug_` 调用，以 403 丢弃，3 分钟内完成全网止血。
2. **第二道防线：云助手穿透恢复控制权（零关机零重启）**
   * 识别出 Geth 进程正常运行出块的前提，坚决否定粗暴关机/重启方案，利用华为云底层 `UniAgent` 云助手在线秒级写回生产公钥，无感夺回 `Rpc1` 权限。
3. **第三道防线：生产集群优雅滚动加固（Rolling Update）**
   * 制定标准滚动重启方案：先在 Nginx 摘除 `Rpc1` -> 流量全走 `Rpc2` -> 修改 `Rpc1` 并重启 Geth -> 挂载 `Rpc1` -> 摘除 `Rpc2` -> 修改 `Rpc2` 并重启 Geth -> 恢复双活。
   * 全网用户与 DApp 调用全流程 100% 连贯，无任何丢包报错。
4. **第四道防线：业务边界精准裁决（保护 Archive-01）**
   * 深入现场日志查明 Blockscout 依赖 `debug_traceTransaction`，果断决定 `Archive-01` 不关停 Geth，而是依靠“公网端口屏蔽 + Nginx Lua 拦截”的双层防护，既保证浏览器功能正常，又确保安全无虞。
